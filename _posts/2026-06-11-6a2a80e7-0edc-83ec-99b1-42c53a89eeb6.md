# 扩散语言模型｜用上下文无关文法约束结构化生成

# 00. 引言：这篇论文想解决什么

这篇论文解决的是一个很工程化、但对扩散语言模型非常关键的问题：模型生成的每一步看似合理，最后结果却不一定满足形式语言约束。典型场景包括 C++ 代码、JSON 结构化输出、SMILES 分子字符串。这些对象不是普通自然语言，而是由严格语法定义的符号系统，局部 token 概率高不代表整体可解析。

传统约束解码主要服务于自回归大语言模型，尤其是从左到右的前缀补全。它可以在生成下一个 token 时判断“这个 token 是否还能构成合法前缀”。但扩散语言模型不是从左到右生成，而是在任意位置逐步填 mask；同时，多区域填空任务也会在多个空洞之间交错生成。因此，传统“前缀合法性检查”失效。

本文的核心突破是把扩散语言模型和多区域填空统一转化为一个更一般的问题：**当前部分输出是否仍然存在某种补全方式，使最终字符串属于目标形式语言**。作者把这个问题称为受约束填空问题，并证明它可以转化为“上下文无关语言与正则语言的交集是否为空”的判定问题。这样，扩散模型每提出一个 token，系统不只判断它局部是否合法，而是判断加入这个 token 后，剩余空洞是否仍有可能补成合法程序、合法 JSON 或合法 SMILES。

全文主线可以概括为：**用正则语言描述“当前部分输出的所有可能补全”，用上下文无关文法描述“目标语言的合法语法”，通过交集非空性判断 proposal 是否可接受，再把这个判断嵌入扩散语言模型采样过程。**

# 01. 背景问题：为什么这件事难

## 1. 扩散语言模型的生成顺序破坏了传统约束解码假设

自回归模型的生成顺序是线性的。假设已经生成前缀 `int main(`，约束解码只需要判断下一个 token 是否能接在这个前缀后面，并且仍可能形成合法程序。

扩散语言模型不同。它从一个全 mask 或部分 mask 序列出发，每一步选择某个位置，把 mask 替换成 token。例如一个函数可能先生成 `return`，后生成函数名，最后生成返回值。论文在第 2 页图 1 和第 4 页图 2 中明确展示了这种“非从左到右”的生成模式：每一步模型给出一个插入位置和一个 token，约束系统需要判断该 proposal 是否会让整体任务不可补全。〔引用待核〕

这导致一个关键难点：**不能只看当前 token 是否局部合法，而要判断所有空洞是否还能共同形成一个全局合法字符串。**

## 2. 多区域填空比单区域填空更接近真实代码编辑

论文讨论了四类生成范式：

- 前缀补全：固定前缀，生成后续内容。
- 中间填空：固定前缀和后缀，生成中间内容。
- 多区域填空：多个固定片段之间存在多个待填区域。
- 扩散语言模型：mask 分布在任意位置，生成顺序不固定。

多区域填空和扩散生成本质上都是“多个空洞之间协同补全”。例如：

```text
int ____() { ______ 2; }
```

函数名、返回语句、符号闭合都可能互相约束。某一步生成 `foo()` 看起来像合法标识符的一部分，但放进函数定义后可能导致 `int foo()() { ... }` 这种不可补全结构。论文图 1 就用这个例子说明：`foo()` 被拒绝，`foo` 被接受。〔引用待核〕

【背景知识：上下文无关文法与正则语言】

正则语言适合描述线性模式，例如“某些固定片段按顺序出现，中间可以插入任意字符”。上下文无关文法更强，能描述嵌套结构，例如括号匹配、代码块嵌套、JSON 对象、SMILES 分支括号等。

这篇论文利用了一个经典形式语言结论：

\[
\text{上下文无关语言} \cap \text{正则语言} = \text{上下文无关语言}
\]

也就是说，如果目标语法是上下文无关文法，当前部分输出的所有补全是正则语言，那么二者的交集仍然可以用上下文无关文法表示。接下来只需要判断这个交集语言是否为空。

# 02. 方法核心：作者到底做了什么

## 1. 把约束解码统一为“可补全性判断”

作者定义部分输出为：

\[
x = x_1 \square x_2 \square \cdots \square x_n
\]

其中 \(x_i\) 是已经固定的字符串，\(\square\) 是待填区域。受约束填空问题就是判断是否存在若干字符串：

\[
y_1, y_2, \ldots, y_{n-1}
\]

使得：

\[
w = x_1 y_1 x_2 y_2 \cdots y_{n-1} x_n \in L
\]

这里 \(L\) 是目标语言，例如合法 C++、合法 JSON、合法 SMILES。

这个定义的意义在于：模型每生成一个 token 后，系统不需要知道最终答案是什么，只需要判断“是否仍然存在至少一种合法补全”。如果不存在，说明这个 token 已经把生成路径带进死胡同，必须拒绝。

## 2. 用正则语言描述“当前部分输出的所有补全”

对于一个部分输出 \(x = x_1 \square x_2 \square \cdots \square x_n\)，所有可能补全可以描述为：

\[
C_x = x_1 \Sigma^* x_2 \Sigma^* \cdots \Sigma^* x_n
\]

也就是固定片段必须按顺序出现，中间空洞可以插入任意字符串。这个语言是正则语言，可以用有限自动机表示。论文第 4 页图 2b 给出了对应自动机：固定片段对应确定路径，空洞区域对应 \(\Sigma^*\) 自环。〔引用待核〕

这个设计的关键直觉是：**不要直接枚举所有补全，而是用一个自动机压缩表示所有补全空间。**

## 3. 用交集非空判断 proposal 是否可接受

目标语言 \(L\) 由上下文无关文法描述，当前补全空间 \(C_x\) 是正则语言。当前部分输出是否可补全，等价于：

\[
L \cap C_x \neq \emptyset
\]

如果交集为空，说明不存在任何方式能把当前部分输出补成合法字符串；如果非空，说明至少还有一条合法生成路径。

扩散语言模型采样时，流程变成：

```text
模型提出一个 token 和插入位置
更新部分输出
构造当前补全语言 C_x
判断 L ∩ C_x 是否为空
非空：接受 token
为空：拒绝 token，重新采样
```

这种方法和传统 token mask 的区别很大。传统方法通常判断“下一个 token 是否属于合法候选集合”；本文判断的是“加入 token 后，整个剩余问题是否仍有解”。

## 4. 为工程效率改造交集算法

标准算法虽然可行，但代价很高。若目标文法有 \(|V|\) 个非终结符，自动机有 \(|Q|\) 个状态，交集文法的非终结符规模会达到：

\[
O(|V||Q|^2)
\]

产生式甚至可能达到：

\[
O(|P||Q|^3 + |P||Q|^2|\Sigma|)
\]

这对每一步采样都要运行的解码过程非常重。

作者做了三类优化：

- 不使用标准乔姆斯基范式，而使用允许空产生式和单元产生式的 \(C2F+\epsilon\) 范式，减少文法膨胀。
- 不显式构造完整交集文法，只在需要时隐式搜索。
- 只追踪能生成终端字符串的非终结符，避免处理大量无效符号。

# 03. 关键机制拆解：最值得理解的技术点

## 1. “可补全性”比“当前合法性”更适合扩散模型

扩散模型生成时，许多位置尚未确定。因此，一个 proposal 是否合理，不能由局部片段判断。

例如当前序列：

```text
C6CCCC⊥))
```

表面上剩下一个 mask，但已经出现了过多右括号。模型如果继续填普通 token，很可能无法修复括号结构。论文在第 25 页图 6b 展示了类似 SMILES 案例：LLADA 8B 留下单个 mask，但剩余 token 数不足以满足语法补全需求。〔引用待核〕

所以本文检查的是：

\[
\exists y_1,\ldots,y_{n-1},\quad x_1y_1x_2\cdots y_{n-1}x_n \in L
\]

这其实是在问：**当前状态是否还活着。**

对 DiffTok-Mol 这类 SMILES 条件生成任务，这个思想非常重要。因为 SMILES 的错误往往不是某个 token 单独非法，而是环编号、括号、芳香性、支链闭合在全局上不一致。扩散模型按置信度逐步填 token 时，很容易出现“每一步都像对的，整体却错”的问题。

## 2. 交集语言构造：把语法约束和当前状态绑定

作者构造的交集文法非终结符形式为：

\[
{}^p\!A^q
\]

含义是：原始文法中的非终结符 \(A\)，生成一个字符串后，能够让自动机从状态 \(p\) 转移到状态 \(q\)。

这相当于把两套系统绑定在一起：

- \(A\)：目标语言的语法结构。
- \(p \rightarrow q\)：当前部分输出补全自动机允许的路径。

交集文法的规则大致如下：

\[
A \rightarrow \sigma
\]

对应：

\[
{}^p\!A^q \rightarrow \sigma,\quad \text{if } \delta(p,\sigma)=q
\]

如果原文法有：

\[
A \rightarrow BC
\]

那么交集文法需要枚举中间状态 \(r\)：

\[
{}^p\!A^q \rightarrow {}^p\!B^r \; {}^r\!C^q
\]

含义是：\(B\) 生成的部分把自动机从 \(p\) 带到 \(r\)，\(C\) 生成的部分再从 \(r\) 带到 \(q\)。这样，语法推导和自动机路径必须同时成立。

这个机制的核心价值是：**它不是用规则硬剪 token，而是把“当前 partial output 的可补全路径”嵌入语法推导过程。**

## 3. 词法分析问题：LLM token 和形式语言终结符不一致

论文很重视一个容易被忽略的工程问题：大语言模型输出的是字符或子词 token，而形式文法通常作用于词法单元，例如：

```text
<number>
<identifier>
<if>
<while>
```

例如 `1234 hello12` 在语法层可能是：

```text
<number> <identifier>
```

但在部分输出中，空洞可能切开一个词法单元：

```text
123 □ 789
```

它既可能是两个数字 token，也可能被补成一个完整数字。论文附录 C 专门处理了“词法单元跨越填空区域”的情况，并构造能同时容纳多种词法解释的自动机。〔引用待核〕

这对 SMILES 尤其关键。因为 SMILES 中很多符号具有多字符结构，例如：

```text
Cl
Br
@@
[Na+]
%12
```

如果约束系统只按字符或模型 token 粗暴判断，很容易误杀合法路径，或者放过非法路径。本文的方法本质上要求在 tokenizer 层和 grammar 层之间建立一个可靠映射。

# 04. 实验验证：结果到底说明了什么

## 1. 多区域代码填空：语法正确率显著提升，功能正确率小幅提升

作者在 C++ HumanEval-X 上构造 1、2、3 个区域的多区域填空任务。对 StarCoder2、CodeGemma、DeepSeek Coder 系列模型测试。

结果很清楚：

- 区域越多，普通生成的语法正确率越差。
- 约束解码显著提升语法正确率。
- 用交集语言自动补全失败样本后，语法正确率进一步接近满分。
- 功能正确率也提升，但幅度明显小于语法正确率。

例如 3 区域填空中，普通生成的语法正确率经常只有 20%～36%，约束后可以提升到 83%～96%。功能正确率提升通常只有几个百分点。论文表 1 给出了完整结果。〔引用待核〕

技术含义是：**语法约束能有效消除低级结构错误，但不能自动解决算法语义错误。**  
模型如果写错逻辑、边界条件或算法复杂度，文法约束并不能修复。

## 2. 扩散语言模型：语法几乎可控，但语义能力仍是瓶颈

作者测试了四个扩散语言模型：

- LLaDA 8B
- Dream 7B
- DreamCoder 7B
- DiffuCoder 7B

任务包括 C++、JSON、SMILES。

表 2 显示，约束解码对语法正确率提升非常明显。以 SMILES 为例，普通生成的语法正确率大约在 58%～73%，约束后可提升到 91%～95%；如果使用自动合法补全，接近 99%～100%。JSON 任务中，约束补全后达到 100% 语法正确率。〔引用待核〕

但功能正确率提升有限，尤其是 SMILES。普通模型在 SMILES 任务上的功能正确率平均很低，约束只能带来约 0.2% 的平均提升。这里的“功能正确率”不是语法有效，而是生成分子是否与目标描述对应。论文用 RDKit 解析后比较 canonical 表示。〔引用待核〕

这说明一个关键边界：**文法约束可以让 SMILES 可解析，但不能保证分子语义正确。**

对分子生成来说，这一点很重要。合法 SMILES 只是最低门槛。模型还需要满足目标片段、药效团、性质、结合口袋或文本描述。本文解决的是“语法层约束”，不是“化学语义层约束”。

## 3. 运行开销可接受，但不是免费

多区域填空中，约束解码的中位 token 级开销约为 125%。模型越小，约束部分相对越贵；模型越大，模型推理本身更慢，约束开销占比反而较低。区域越多，自动机和交集搜索越复杂，开销也越大。论文表 3 中，3 区域任务开销明显高于 1 区域任务。〔引用待核〕

扩散模型中，总完成时间中位开销约为 30%。某些情况下还可能加速，因为无效路径会被提前中止。论文表 4、表 6 进一步展示了不同 diffusion steps 下的开销变化。〔引用待核〕

工程结论：**这套方法适合作为高价值生成任务的推理期校验器，但如果每一步都做完整约束检查，仍需优化缓存、增量解析和 grammar 编译。**

# 05. 这项工作的真正价值

这篇论文的价值不是“让模型更聪明”，而是把扩散语言模型接入了形式语言约束系统。

它改变了一个默认假设：约束解码不必绑定自回归前缀生成。只要把当前部分输出表示为“固定片段 + 空洞”，就可以用统一的可补全性判断处理前缀补全、中间填空、多区域填空和扩散生成。

对后续研究最有影响的点有三个：

1. **扩散语言模型可以做严格结构化输出**  
   这让扩散模型不只适合自由文本，也能进入代码、JSON、配置文件、分子字符串等强语法场景。

2. **SMILES 生成可以引入 grammar-level hard constraint**  
   对 DiffTok-Mol 这类模型，本文提供了一个直接可迁移的方向：采样过程中每次填 token 后，用 SMILES 上下文无关文法判断剩余 mask 是否仍可补全。

3. **多区域条件生成可以被形式化处理**  
   linker design、fragment decoration、motif completion 本质上都像多区域填空。只要条件片段能映射成固定字符串，剩余区域就可以走本文的可补全判定框架。

这项工作解决的是“生成过程的语法可靠性”，不是模型表征能力本身的突破。它更像是一个推理期安全层：把原本概率生成的过程投影到形式语言允许的空间内。

# 06. 局限与需要验证的点

1. **上下文无关文法只能覆盖语法，不能覆盖完整语义**  
   C++ 类型正确性、变量作用域、函数签名一致性、SMILES 价态合理性、芳香性化学有效性，都不一定能由普通上下文无关文法完整表达。

2. **SMILES 的“语法正确”不等价于“化学正确”**  
   论文用 SMILES 任务证明语法正确率可显著提升，但功能正确率几乎没有明显改善。这说明 grammar 只能保证可解析，不能保证生成的是目标分子。〔引用待核〕

3. **固定长度 mask 与任意长度补全之间存在近似误差**  
   论文承认，算法在构造补全语言时允许空洞填入任意长度字符串，但实际扩散模型的 mask 数量有限。这会造成“理论上可补全，但剩余 token 数不够”的情况。第 25 页图 6 就展示了这类残余错误。〔引用待核〕

4. **自动合法补全可能脱离模型分布**  
   Con. 模式会在模型多次失败后，从交集语言中采样一个合法补全。这能提升语法正确率，但这个补全不一定是模型高概率输出，也不一定语义合理。

5. **工程集成仍有成本**  
   需要准备目标语言文法、词法规则、token 与 lexeme 的映射、自动机优化、Rust/Python 混合实现。对分子任务而言，还需要处理 SELFIES、SAFE、BPE、SPE、atom-level tokenizer 与 SMILES grammar 的对齐问题。

# 07. 总结与延伸探讨

这篇论文最值得记住的点是：**扩散语言模型的约束解码不应模仿自回归前缀约束，而应转化为“当前部分输出是否仍可补全”的全局判定问题。**

对代码和 JSON，它能显著减少结构错误；对 SMILES，它能显著提高语法有效性，但不能单独解决化学语义和目标一致性问题。

对 DiffTok-Mol 这类模型，最直接的启发是：

```text
每次填入 token 后，不只看 token 置信度；
还要判断当前 SMILES partial sequence 是否仍存在合法补全。
```

更进一步，可以把本文的 grammar constraint 和分子约束分层组合：

```text
第 1 层：SMILES 上下文无关文法，保证语法可补全
第 2 层：RDKit 轻量校验，过滤价态/芳香性/环闭合问题
第 3 层：任务约束，保证片段、linker、motif、性质或口袋条件被满足
第 4 层：重掩码策略，对局部高置信但全局不一致区域重新采样
```

这篇工作给出的不是最终分子生成方案，而是一个很强的推理期基础设施：让扩散语言模型从“概率填空器”变成“受形式语言约束的可补全生成器”。
